## Rust single-loader migration analysis

This run uses commit `658d6dfc9d`, which moves cache lookup, source hashing,
dependency replay, JSON persistence, and hit restoration from the JavaScript
loader runner into Rust. A cacheable JavaScript loader now yields exactly one
loader on a miss and returns to Rust before the next loader can run.

```text
Rule.use options
  stable options fingerprint in the JS config adapter
       ↓
NormalModuleFactory
  CachedLoader(loader identifier + options hash)
       ↓
Rust loader runner before_normal
  hash actual input Content + lookup Rust LoaderCacheService
       ├─ hit: restore Content/source map/dependency deltas, skip JS
       └─ miss: yield exactly one JS loader
                    ↓
Rust loader runner after_normal
  validate cacheable/diagnostics/additionalData
  persist the individual loader result
```

Compared with the previous JavaScript implementation in
`result-2026-08-06-10-17-03.md`, the warm path improved materially:

| Scenario | Previous JS cache | Rust cache | Change |
| --- | ---: | ---: | ---: |
| backend-only warm | 480.9 ms | 271.5 ms | -43.5% |
| slow-loader warm | 638.4 ms | 445.8 ms | -30.2% |

This confirms that the former JavaScript-side stable serialization, hashing,
`outputFileSystem` reads, and `JSON.parse` work were a major part of the old
warm overhead. The distributions are also reasonably stable: Rust
single-loader warm ranges from 250.9–317.4 ms for `backend-only` and
439.5–465.9 ms for `slow-loader`.

The Rust single-loader cache is still slower than the whole-chain JSON cache on
warm builds: +29.8% for `backend-only` and +85.2% for `slow-loader`. This is an
expected remaining granularity cost rather than a cache miss: all 1,000 entries
are present, and the slow-loader warm build is 27.96x faster than its cold
build. Each module still performs an input-content hash, loader-file metadata
lookup, individual cache-file read, JSON decode, and dependency-delta restore.
The whole-chain cache can return the final chain result directly, while the
single-loader design must preserve a boundary around every cacheable loader.

Cold `backend-only` is slower than the previous JS implementation (805.9 ms
versus 568.0 ms) because the Rust file store uses an atomic temp-file write,
per-entry lock, and `fsync`; those durability costs dominate an identity loader.
For the realistic slow loader, cold time is dominated by Babel execution and
the Rust version is within normal run-to-run variance while recording a lower
median in this run.

The next performance work should target the remaining Rust storage overhead:
avoid repeated metadata work for the same loader while preserving watch-mode
invalidation, reduce duplicated key data in each JSON payload, and batch or
shard persistent reads/writes. Changing serialization alone is unlikely to
close the gap because rkyv and JSON whole-chain warm medians differ by only
2–7 ms in this run.
