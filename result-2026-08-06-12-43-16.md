## Rust single-loader migration analysis

Commit `e03e9cf148` moves cache lookup, source hashing, dependency replay,
JSON persistence, and hit restoration from the JavaScript loader runner into
Rust. A cacheable JavaScript loader yields exactly one loader on a miss and
returns to Rust before the next loader can execute.

```text
Rule.use options
  stable options fingerprint in the JS config adapter
       ↓
NormalModuleFactory
  CachedLoader(loader identifier + options hash)
       ↓
Rust loader runner before_normal
  hash actual input Content + query LoaderCacheService
       ├─ hit: restore Content/source map/dependency deltas, skip JS
       └─ miss: yield exactly one JS loader
                    ↓
Rust loader runner after_normal
  validate cacheable/diagnostics/additionalData
  persist the individual loader result
```

Compared with the previous JavaScript implementation in
`result-2026-08-06-10-17-03.md`, the Rust warm path improved materially:

| Scenario | Previous JS cache | Rust cache | Change |
| --- | ---: | ---: | ---: |
| backend-only warm | 480.9 ms | 273.3 ms | -43.2% |
| slow-loader warm | 638.4 ms | 433.2 ms | -32.1% |

The internal counters prove that the remaining warm time is not caused by
failed cache lookup: both scenarios hit all 1,000 entries and yield to JS zero
times. Hash plus JSON deserialization takes about 10.0 ms for `backend-only`
and 29.8 ms for `slow-loader`, only a small part of the 273.3/433.2 ms total.

The main remaining difference from whole-chain JSON is execution position.
The whole-chain cache can hit during pitch and return the final chain result
without reading the original module resource. A single-loader key contains the
actual input `Content`, so the runner must first process/read the resource (or
run loaders to its right), hash that input, then read its individual cache file.
In this one-loader benchmark the warm single-loader path therefore reads both
the source set and 1,000 cache files; the metrics show the latter account for
781.1 KiB in `backend-only` and 10.3 MiB in `slow-loader`. Loader-file metadata,
dependency replay, task scheduling, and content copies add smaller unmeasured
costs around those reads.

This makes the +37.5% (`backend-only`) and +83.6% (`slow-loader`) warm gap to
whole-chain JSON a real granularity tradeoff, not a correctness failure. The
single-loader cache is useful when uncached loaders to the left must still run
or loaders to the right produce reusable intermediate input; this synthetic
one-loader chain is the best case for whole-chain caching.

Cold `backend-only` remains slower than the previous JS implementation because
the Rust store uses an atomic temp-file write, per-entry lock, and `fsync` for
each result. For `slow-loader`, Babel execution dominates and the Rust median is
within 1% of JSON. The next optimizations should focus on avoiding repeated
loader metadata work, reducing durable-write overhead, and batching/sharding
cache reads. Changing serialization alone is unlikely to close the gap: rkyv
and JSON whole-chain warm medians differ by only a few milliseconds here.
